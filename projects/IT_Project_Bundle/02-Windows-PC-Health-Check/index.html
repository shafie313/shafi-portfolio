Windows PC Health Check

A read-only PowerShell snapshot for Windows 10/11 that gathers computer, operating-system, processor, memory, fixed-disk, network and selected service details into timestamped CSV and HTML reports.

This page documents the included script and its intended behavior. No completed run, sample report or successful test result is supplied with the project.

01 / PROJECT OVERVIEW

Turn routine checks into a readable snapshot

The toolkit collects selected workstation information and formats the checks as rows with a timestamp, category, check name, value and status. It is intended to support investigation, not make a definitive health judgment or repair the computer.

Objectives

  • Collect common Windows support details in one repeatable run.
  • Identify disk free-space values and selected Windows service states for follow-up.
  • Export the collected rows to CSV and a simple HTML report for review.
  • Keep checks read-only; the script does not change Windows configuration.
02 / ENVIRONMENT & TOOLS

Windows desktop support context

  • Windows 10/11 test computer and Windows PowerShell 5.1 or newer.
  • Standard user rights are sufficient for most checks; some details may be unavailable.
  • PowerShell CIM queries for OS, CPU and logical-disk information.
  • Get-NetIPConfiguration for IPv4, gateway and DNS information.
  • Get-Service for the configured service checks: Spooler, Dhcp, Dnscache and Winmgmt by default.

Before running: Review the PowerShell source and use a test computer you own or are authorized to support. Follow organizational execution-policy requirements.

03 / STEP-BY-STEP IMPLEMENTATION

Run the toolkit and inspect both reports

  1. Copy the project folder to a Windows 10/11 test computer and inspect Windows-PC-Health-Check.ps1.
  2. Open PowerShell in the project folder and run the script for the current session only if permitted by the device's organizational policy.
  3. The script creates a Reports folder beside the script by default and generates a timestamp for the output filenames.
  4. Review the CSV rows and open the HTML report. Treat CHECK and WARNING as prompts to investigate, not proof of a fault.
  5. Document any missing command output or unavailable system detail rather than assuming the check passed.
powershell.exe -NoProfile -ExecutionPolicy RemoteSigned -File .\Windows-PC-Health-Check.ps1

Use only when allowed by your organization's policy. Do not bypass execution policy.

05 / TROUBLESHOOTING

Interpret the report carefully

  • System query warning: review the message recorded by the script; CIM or a requested system property may be unavailable.
  • Disk warning: the source marks a fixed volume below 10% free as WARNING. Confirm capacity and usage before deciding next steps.
  • Service marked CHECK: confirm the service is installed and whether its current state is expected; a non-running service is not automatically a fault.
  • Missing network data: review the adapter's connection state and available permissions, then compare with Windows network settings.
  • Report not found: check the configured output folder and permissions; the default path is the script's Reports directory.
06 / SCREENSHOTS & EVIDENCE

No captured evidence is included

The supplied project files contain the script and run instructions, but no screenshots or generated reports. After an authorized test run, evidence could include the HTML report, selected CSV rows and a redacted PowerShell session view.

Protect data: Remove hostnames, user details, IP information or other sensitive values before sharing any real system report.

07 / RESULTS & KEY LEARNINGS

Structured outputs, not claimed test results

The documented result of running the script is a timestamped CSV and HTML report. No report has been included here, so no measured health result or successful execution is claimed.

  • Separate observed system values from status labels that need human interpretation.
  • Use repeatable, read-only checks to gather useful context before troubleshooting.
  • Review the output for missing data and protect endpoint information when sharing evidence.
